# 멀티채널 FAST 병렬성 검증 (sample.cfg 기준)

FAST(Fully-Associative Sector Translation, `MappingMode = 1`)를 슈퍼블록 방식(`SuperblockSize = C`)으로 멀티채널화했을 때, 채널 수를 늘리면 처리량이 늘어나는지 확인한 결과이다. GC(Garbage Collection, 가비지 컬렉션)가 일어나지 않는 상태(채움 0%)에서 `config/sample.cfg`의 구조를 그대로 두고 채널 수만 바꿔서 측정했다.

## 요약

- 요청이 큰 쓰기(합성 순차 쓰기, `copyHtoD`)에서는 채널 1개 → 8개에서 처리량이 약 **6.2배**가 되었다(채널 8개의 병렬 효율 78%).
- nexus5 trace 22종 전체에서 채널 8개 처리량 ÷ 채널 1개 처리량의 **산술평균은 1.80**, 중앙값은 1.27이었다. 22종 중 4 이상인 trace는 2종, 2 미만인 trace는 18종이다.
- 이 비율은 쓰기 요청 크기에 크게 좌우된다(trace별 쓰기 평균 요청 크기와 채널 8개 처리량 비의 피어슨 상관계수 0.96). 쓰기 요청이 10~30KB인 앱 trace의 처리량 비는 1.0~1.4에 그친다.
- 모두 GC가 없는 조건의 값이다. 디스크가 차서 merge가 많아지는 조건의 결과는 이 문서에 포함하지 않았다.

## 측정 지표와 식

- 처리량 (MB/s)
  - 합성 순차 쓰기: `처리량 = 2048 MB ÷ 시뮬레이션 시간(초)`
  - trace: `처리량 = trace 전체 데이터량(읽기 + 쓰기, MB) ÷ 시뮬레이션 시간(초)`
  - 시뮬레이션 시간은 시뮬레이터 출력의 `Tick` 값(단위 ps)을 10^12로 나눈 값이다.
- 처리량 비 (채널 N개) : `처리량 비 N/1 = 채널 N개일 때의 처리량 ÷ 채널 1개일 때의 처리량`
- 병렬 효율 (채널 N개) : `병렬 효율 = 처리량 비 N/1 ÷ N × 100 (%)` (채널 수에 정확히 비례해 늘면 100%)
- WAF (Write Amplification Factor, 쓰기 증폭 계수) : `WAF = NAND에 쓴 sector 수 ÷ 호스트가 쓴 sector 수` (통계 `ftl.fast.waf`). merge가 없으면 1.00이다.

## 측정 조건

`config/sample.cfg`에서 아래 값만 바꿨다.

| 항목 | 값 |
|---|---|
| `[ftl]` `MappingMode` | 1 (FAST), 비교용으로 0 (page mapping) |
| `[pal]` `Channel` | 1, 2, 4, 8 |
| `[icl]` `EnableWriteCache` | 0 |
| 그대로 둔 값 | `SuperblockSize = C`, `Package = 4`, `Die = 2`, `Plane = 2`, `Block = 512`, `Page = 512`, `PageSize = 16384`, `OverProvisioningRatio = 0.25`, `FillRatio = 0.0`, `InvalidPageRatio = 0.0`, `FASTRWLogBlocks = 8` |

- `[dram]`에도 `Channel`이 있으므로 NAND 채널은 `[pal]` 섹션의 값만 바꾼다.
- 채널을 늘려도 채널당 구조(패키지 4, 다이 2)는 같으므로 용량이 채널 수에 비례해 커진다.
- 각 조합은 1회 실행했다. 시뮬레이터는 같은 입력에서 같은 결과를 낸다.

워크로드는 두 종류이다.

1. 합성 순차 쓰기: 시뮬레이션 설정에서 `Mode = 0`, `io_size = 2G`, `readwrite = write`, `blocksize = 128K`.
2. nexus5 trace: 시뮬레이션 설정에서 `Mode = 1`, `[trace]`의 `File`에 trace 파일을 지정한다. trace는 바깥 저장소(`simplessd-standalone`)의 `trace/converted/`에 있고 22종을 사용했다.

실행은 `./simplessd-standalone <시뮬레이션 설정> <SimpleSSD 설정> <출력 폴더>`이다.

## 결과 1: 합성 순차 쓰기와 copyHtoD

### 합성 순차 쓰기 2GiB (128KB 요청)

| 지표 | 채널 1개 | 채널 2개 | 채널 4개 | 채널 8개 |
|---|---|---|---|---|
| FAST 처리량 (MB/s) | 43.8 | 75.6 | 141.5 | 273.9 |
| FAST 처리량 비 N/1 | 1.00 | 1.73 | 3.23 | 6.25 |
| FAST 병렬 효율 (%) | 100 | 86 | 81 | 78 |
| FAST WAF | 1.00 | 1.00 | 1.00 | 1.00 |
| page mapping 처리량 (MB/s) | 266.2 | 532.6 | 1065.6 | 2130.8 |
| page mapping 처리량 비 N/1 | 1.00 | 2.00 | 4.00 | 8.00 |

### copyHtoD trace (쓰기 위주, 평균 요청 466KB)

| 지표 | 채널 1개 | 채널 2개 | 채널 4개 | 채널 8개 |
|---|---|---|---|---|
| FAST 처리량 (MB/s) | 32.9 | 58.5 | 109.2 | 205.0 |
| FAST 처리량 비 N/1 | 1.00 | 1.78 | 3.32 | 6.24 |
| FAST 병렬 효율 (%) | 100 | 89 | 83 | 78 |
| FAST WAF | 1.46 | 1.56 | 1.36 | 1.13 |
| page mapping 처리량 (MB/s) | 209.6 | 313.0 | 416.5 | 496.7 |
| page mapping 처리량 비 N/1 | 1.00 | 1.49 | 1.99 | 2.37 |

- 순차 쓰기에서는 merge가 한 번도 일어나지 않았다(WAF 1.00). copyHtoD는 채널 8개에서 partial merge 3번, full merge 8번이 있었다.
- 채널 1개에서 FAST 처리량은 page mapping의 약 1/6이다(순차 쓰기 43.8 vs 266.2 MB/s). FAST는 데이터를 블록 순서대로 쓰기 때문에 채널 안의 여러 칩을 돌려 쓰는 page mapping보다 칩 병렬성을 덜 쓰는 것으로 추정한다(직접 확인하지는 않았다).

## 한계

- 각 조합 1회 실행이다. 결과 1은 워크로드 2종, 결과 2는 FAST만 측정했다.
- 쓰기 캐시 OFF, 채움 0%의 GC 없는 조건이라 병렬성의 상한에 가까운 값이다.
- 시뮬레이션은 요청을 동기로 발행하는 설정(`TimingMode = 0`)으로 실행했다.
- `SuperblockSize = C`만 확인했다. 패키지나 다이를 포함한 슈퍼블록은 시도하지 않았다.
- trace 22종은 `trace/converted/`의 일부이며 Booting 등은 포함하지 않았다.
